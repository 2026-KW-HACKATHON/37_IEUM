# 동시 저장 보호와 표시 수정

## 변경 내용

- 운영자 데이터는 단일 DB 스냅샷으로 읽으며 데이터 버전도 함께 받습니다.
- 저장 시 서버에서 읽었던 버전과 현재 버전을 비교합니다. 다른 사람이 제출·수정·저장했다면 이전 화면의 저장은 거부하고 최신 데이터를 다시 불러옵니다.
- DB에서 비교와 저장은 같은 트랜잭션 안에서 실행합니다. 요청·활동·신청·배정 테이블의 쓰기를 잠깐 직렬화합니다. 읽기는 계속 가능합니다.
- 전체 운영 데이터 중 어느 하나라도 달라지면 재확인이 필요합니다. 같은 학생의 최신 제출물이나 다른 운영자의 새 배정을 덮어쓰거나 삭제하지 않습니다.
- 버전 검사가 없는 기존 저장 RPC의 브라우저 실행 권한을 제거합니다.
- 사용자 관리에서 운영자 계정을 ‘운영자’로 표시하고 유형 필터에도 추가합니다. 운영자 수정·삭제는 계속 차단합니다.
- 학생 ‘이번 달 활동’은 한국 시간 기준으로 이번 달에 내부 인증이 완료된 배정 건을 집계합니다. 누적 인정 시간과 누적 인증 건수는 유지합니다.

## 적용 순서

1. 변경 코드를 PR로 올리고 검토합니다.
2. Supabase SQL Editor에서 `supabase/migrations/20261008030000_admin_state_conflict_guard.sql` 전체를 실행합니다. 기존 마이그레이션 적용을 전제로 합니다.
3. 프론트엔드 PR을 main에 병합하고 Vercel Production 배포 완료를 확인합니다.

SQL 적용과 새 프론트 배포 사이에는 기존 운영자 화면의 저장이 거부됩니다. 운영 작업을 잠시 멈춘 상태에서 두 단계를 연이어 진행하세요.
운영자는 배포가 끝난 뒤 새로고침해야 합니다. 기존 회원 관리 Edge Function을 다시 배포할 필요는 없습니다.
Supabase 설정·실제 DB는 코드 수정 작업에서 자동으로 변경하지 않았습니다.

## 배포 후 확인

서로 다른 브라우저/계정과 테스트 활동을 사용합니다.

1. 운영자 A와 B가 같은 화면을 엽니다. A가 모집 상태를 변경한 뒤 B가 이전 화면에서 저장하면 충돌 안내와 최신 데이터가 나타나야 합니다.
2. 운영자가 화면을 연 뒤 학생이 결과물을 제출합니다. 운영자가 예전 화면에서 다른 운영 변경을 저장해도 학생 제출물은 그대로 남아야 합니다.
3. 충돌 후 최신 정보를 확인하고 다시 저장하면 정상 처리되어야 합니다.
4. 사용자 관리에서 운영자 유형과 운영자 필터를 확인합니다.
5. 지난달·이번 달 인증 기록이 함께 있는 테스트 학생의 월별 건수와 누적 시간·인증 건수를 확인합니다.
