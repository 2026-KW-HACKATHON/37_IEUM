# 운영자 회원 수정과 삭제

사용자 관리 → 기본 정보 보기에서 이름·전화번호를 수정하거나 회원 삭제를 확인합니다.
수정·삭제 사유를 입력해야 합니다. 사유에는 필요 이상의 개인정보를 입력하지 않습니다.
운영자 계정은 이 기능의 수정·삭제 대상에서 제외합니다.

## 수정

- 이름과 전화번호만 변경합니다. 역할·비밀번호·검증 상태·주소는 변경하지 않습니다.
- 번호 변경은 Supabase Auth의 전화번호 로그인용 이메일 별칭에도 반영합니다. 이후 새 번호와 기존 비밀번호로 로그인합니다.
- 회원 요청이나 입력 오류를 확인한 뒤 수정해야 합니다. SMS 번호 소유 확인 기능은 포함되지 않습니다.
- 이전 이름과 번호를 감사 기록에 복사하지 않습니다. 처리자 ID·대상 ID·사유·변경 항목·시각·결과를 기록합니다.

## 삭제

- 이름을 다시 입력하고 삭제 사유를 제출해야 합니다.
- 로그인 계정, 프로필, 해당 회원의 `ieum-private/<회원 ID>/` 파일을 영구 삭제합니다.
- 의뢰·신청·배정·가족 연결 기록이 있는 회원은 삭제하지 않습니다. 봉사 기록을 임의로 지우거나 익명화하지 않습니다.
- 실제 서비스의 탈퇴·보존·파기 정책은 별도로 결정해야 합니다. 이 기능은 연결 기록이 없는 회원 정리를 지원합니다.
- 처리 준비 단계에서 해당 회원의 새 기록 연결과 파일 업로드를 차단합니다. DB 외래키도 연결된 회원의 삭제를 막습니다.
- 파일 저장소와 Auth는 하나의 트랜잭션으로 묶을 수 없습니다. 중간 실패 시 계정은 남고 일부 파일이 삭제됐을 수 있으므로 안내를 확인하고 재시도합니다.

## Supabase 반영 순서

프론트엔드 코드를 올리는 것만으로 서버 기능이 배포되지 않습니다.

1. Supabase SQL Editor에서 `supabase/migrations/20261008020000_admin_user_management.sql`을 한 번 실행합니다. 기존 마이그레이션이 적용된 프로젝트가 전제입니다.
2. Supabase CLI로 해당 프로젝트에 연결한 뒤 프로젝트 루트에서 `supabase functions deploy admin-user-management`를 실행합니다. 루트의 `supabase/config.toml` 설정도 함께 사용합니다.
3. Supabase 기본 서버 환경변수 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`를 사용합니다. 관리자 비밀키를 `VITE_...` 환경변수나 브라우저 코드에 넣지 않습니다.
4. 다른 도메인에서 사용할 경우 Edge Function 서버 secret `IEUM_ALLOWED_ORIGINS`에 허용할 출처를 쉼표로 구분해서 설정합니다. 기본값은 현재 Vercel 주소와 localhost:5173입니다.
5. 프론트엔드 변경을 GitHub에서 검토·병합한 뒤 Vercel에 배포합니다.

JWT 자동 검증을 끈 대신 Edge Function이 직접 `auth.getUser(token)`으로 토큰을 검증하고 DB의 admin 역할을 확인합니다.
잠금·회원 수정·완료 RPC는 service_role만 실행할 수 있습니다.
기존 `saveProfile`로 이름·번호를 직접 변경하려 하면 DB가 거부합니다.

## 배포 후 확인

실제 회원 대신 삭제해도 되는 테스트 계정으로 확인합니다.

1. 운영자가 이름을 수정하고 새로고침해 저장 결과와 이력을 확인합니다.
2. 번호를 수정하고 새 번호로 기존 비밀번호 로그인이 되는지, 이전 번호 로그인이 안 되는지 확인합니다.
3. 다른 회원의 번호로 바꾸면 실패하는지 확인합니다.
4. 일반 사용자 토큰이나 로그인하지 않은 요청으로 서버 변경이 거부되는지 확인합니다.
5. 연결 기록이 없는 테스트 회원을 삭제하고 로그인 불가·프로필 제거·비공개 파일 제거·감사 기록을 확인합니다.
6. 의뢰·신청·배정 기록이 있는 테스트 회원의 삭제가 차단되는지 확인합니다.

처리 도중 서버가 종료되면 `user_management_audit.status = 'pending'`과 회원 잠금이 남을 수 있습니다.
번호 변경의 경우 Auth 이메일과 프로필 번호가 일치하는지, 삭제의 경우 파일과 계정의 잔여 상태를 먼저 확인합니다.
확인 후 서비스 권한의 서버 RPC `finish_ieum_user_management`로 결과를 기록하고 잠금을 해제합니다. 잠금을 무조건 해제하지 않습니다.

로컬 저장소 모드는 기본정보 수정·삭제 차단 검증을 지원합니다. 실제 Auth·파일 삭제는 Supabase 모드에서 수행합니다.
로컬 수정 이력은 해당 회원 데이터에 저장되므로 회원 삭제 시 함께 삭제됩니다. 삭제 감사 이력의 지속 보관은 Supabase 모드에서 지원합니다.
