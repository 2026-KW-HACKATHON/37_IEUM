# 비대면 봉사 운영 흐름

이 문서는 현재 React 앱의 학생·의뢰자·운영자 화면과 로컬/Supabase 저장 흐름을 설명합니다. 신규 로컬 저장소는 테스트 계정이나 샘플 요청을 자동으로 표시하지 않습니다. Supabase 원격 데이터와 브라우저 로컬 데이터는 서로 별도입니다.

## 저장 모드

### 로컬 브라우저 모드

- `VITE_USE_LOCAL_STORAGE=true`이거나 Supabase 접속 정보가 없으면 로컬 모드입니다.
- `ieum.users.v1`에는 브라우저에서 만든 계정이, `ieum.noncontact.v1`에는 의뢰·활동·신청·배정이 저장됩니다.
- 새 저장소는 빈 배열로 시작합니다. 데이터는 현재 브라우저에만 남고, 다른 기기나 원격 Supabase와 공유되지 않습니다.
- `ieum.tasks.v1`은 기존 대면용 모듈의 별도 저장 키이며 현재 비대면 운영 데이터와 섞이지 않습니다.
- 저장된 값이 손상되었거나 저장에 실패하면 기존 데이터를 조용히 덮어쓰지 않고 작업을 중단합니다.

### Supabase 모드

- `VITE_USE_LOCAL_STORAGE`가 `true`가 아니고 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`가 설정되어야 연결됩니다.
- 사용자 인증·프로필, 요청·활동·신청·배정 및 비공개 파일을 원격 서비스에 저장합니다.
- 초기 SQL 스키마와 이후 마이그레이션, RLS 정책, 필요한 Auth/SMS 설정을 Supabase 프로젝트에 적용해야 합니다.
- 사용자 화면은 `/`, 운영자 로그인과 화면은 `/admin`에서 진입합니다. 두 경로는 같은 앱과 Supabase를 사용합니다. `/admin` 경로만으로 운영자 권한이 생기지 않으며, Supabase 모드에서는 프로필의 `role = admin`이 필요합니다. 로컬 모드의 개발용 운영자 진입 버튼은 `/admin`에서만 표시됩니다.

## 역할별 처리

### 의뢰자

1. 본인 또는 가족으로 가입하고 휴대전화 인증을 마칩니다.
2. 운영자가 주소를 확인해 승인하면 도움 요청을 제출할 수 있습니다.
3. `요청 접수` → `운영자 검토` → `승인`, `반려` 또는 `수정 요청` 상태를 확인합니다.
4. 승인된 요청은 운영자가 봉사활동으로 등록하고 모집을 시작합니다.
5. 결과 확인은 요청에 연결된 활동과 내부 인증된 최신 제출물을 통해 이루어집니다.

### 운영자

1. 요청 내용을 검토하고 처리 사유와 함께 검토 상태를 저장합니다.
2. 승인된 요청 하나에 봉사활동을 하나 등록합니다. 이 시점에는 활동의 `status`가 `모집 중`이어도 `recruitmentOpen`은 `false`입니다.
3. 봉사활동 관리에서 모집을 시작하고 활동 안내를 작성합니다.
4. 신청 내역을 확인합니다. 주소/재학 검증이 승인된 학생만 배정할 수 있으며, 중복 배정과 정원 초과는 거부됩니다.
5. 제출된 결과를 검토해 보완을 요청하거나 승인합니다. 승인 후 내부 인증 번호와 근거를 기록하면 봉사자 배정 상태가 `인증 완료`가 됩니다.

### 대학생

1. 가입 후 재학 증빙 확인 승인을 받아야 모집 중인 활동을 확인·신청할 수 있습니다.
2. 모집 중인 활동은 운영자가 모집을 열었고, 완료·취소되지 않았으며, 정원이 남은 활동입니다. 요청 승인만 된 항목이나 모집 시작 전 활동은 목록에 표시되지 않습니다.
3. 신청 후 운영자 배정을 기다립니다. 시작일이 되면 화면에서 `진행 중`으로 표시됩니다. Supabase 배정 레코드는 학생이 결과를 제출할 때 서버 함수가 시작일을 확인한 뒤 상태를 갱신합니다.
4. 시작일 이후 결과물·활동일지·증빙 설명을 제출할 수 있습니다. 보완 요청을 받은 경우 다시 제출할 수 있습니다.
5. 내부 인증 전 활동은 `내 진행 중 활동`, 인증을 마친 활동은 `완료한 활동`에 표시됩니다.

## 상태 흐름

- 요청: `요청 접수` → `운영자 검토` → `승인` / `반려` / `수정 요청`.
- 배정별 활동: 화면에서는 `봉사자 배정` → 시작일 도래 시 `진행 중` → `결과물 제출` → `검토 중` → `승인` → `인증 완료`로 표시합니다. Supabase는 제출 함수가 시작일을 확인할 때 저장 상태를 `진행 중`으로 갱신합니다.
- 보완: `검토 중` → `보완 요청` → 학생 재제출 시 `재제출` → `검토 중`.
- 모집 가능 여부는 활동 상태만으로 판정하지 않습니다. `recruitmentOpen` 및 남은 정원을 함께 확인합니다.
- 한 활동에 여러 봉사자가 배정되면 개인 상태는 각각 `assignments`에 저장합니다. 활동의 통합 상태와 학생별 진행 상태는 다를 수 있습니다.

## 내부 인증과 공식 실적

운영자는 최신 결과물·활동일지·증빙을 검토하고 제출 활동 시간 이하의 인정 시간을 기록합니다. 0분 기록도 허용됩니다. 결과 승인 후 내부 기록 번호와 근거를 등록하면 서비스 내부 인증이 완료됩니다. 기관의 실적 승인과 1365 등록은 별도 절차이며 현재 자동 연동되지 않습니다.

## 확인 및 테스트

1. 로컬 모드는 새 브라우저 저장소에서 시작해 사용자를 직접 가입시킵니다. 운영자 테스트 진입은 로컬 모드 시작 화면의 개발용 버튼을 사용합니다.
2. Supabase 모드는 SQL migration을 순서대로 적용한 프로젝트와 Auth 설정이 필요합니다. 운영자 프로필은 신뢰할 수 있는 계정만 별도로 승격합니다.
3. 로컬 데이터는 Supabase에 보이지 않으며, 로컬 테스트 계정이 원격 사용자로 자동 이전되지 않습니다.
4. 상태 로직 테스트:

   ```sh
   node --test --test-isolation=none tests/noncontactStore.test.js
   ```
